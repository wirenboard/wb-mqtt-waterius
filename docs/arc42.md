# Архитектура wb-mqtt-waterius (arc42)

---

## 1. Введение и цели

### 1.1. Описание задачи

`wb-mqtt-waterius` — сервис-мост, отправляющий показания счётчиков, подключённых к
контроллеру Wiren Board, в облако [Waterius](https://waterius.ru) через универсальный
HTTP API (`https://uc.waterius.ru`). Сервис читает значения из MQTT-топиков контроллера,
зеркалит их в свои WB-устройства и в заданное время по выбранным дням недели отправляет
`POST` в облако.

Направление интеграции — от Wiren Board в чужой API (не путать с железкой Waterius, которая
шлёт данные в обратную сторону). Аппаратный Waterius не нужен — источником может быть любой
топик контроллера (импульсный счётчик на входах, Modbus, wb-rules).

### 1.2. Функциональные требования

- Список устройств: один ключ Waterius = одно устройство = до 4 каналов (`ch0..ch3`)
- Канал = MQTT-топик источника (`device/control`) + тип счётчика (`data_type` 0..9) + опциональный серийный номер
- Отправка по расписанию: время (`ЧЧ:ММ`) + дни недели (минимум один)
- Плановый фаер раз в день шлёт все устройства свежими значениями, ошибочные добиваются отдельно до конца дня (правила в 4.4)
- Ручная разовая отправка через CLI (`wb-mqtt-waterius send`, флаг `--dry-run` собирает payload без отправки)
- Переключатель автоотправки в UI (гейтит только расписание, не ручной запуск)
- Значение из топика уходит как есть, без пересчёта (топик уже в единицах Waterius)
- Статус интеграции и ошибки видны в веб-интерфейсе

### 1.3. Качественные цели

| Приоритет | Цель          | Описание                                                              |
| --------- | ------------- | --------------------------------------------------------------------- |
| 1         | Надёжность    | Не потерять и не сдвинуть показания, пережить рестарт брокера/сервиса |
| 2         | Прозрачность  | Понятный статус в UI, честные ошибки, без ложного «успеха»            |
| 3         | Простота      | Минимальная настройка, дефолт «только установил» без падений          |
| 4         | Совместимость | Канон свежих WB-python-пакетов, стиль как у wb-mqtt-zigbee            |

### 1.4. Стейкхолдеры

| Роль                     | Ожидания                                                    |
| ------------------------ | ----------------------------------------------------------- |
| Пользователь контроллера | Настроить ключ и каналы в UI, видеть что и когда отправлено |
| Разработчик Waterius     | Приём показаний по документированному протоколу             |
| Команда Wiren Board      | deb-пакет, systemd-сервис, сопровождаемый Python-код        |

## 2. Ограничения

### 2.1. Технические

- Python 3 (dev — 3.11, целевая — Debian на контроллере)
- Runtime-зависимости: `python3-wb-common` (MQTT-клиент поверх paho), `python3-requests`
- Транспорт до брокера — unix-сокет `/var/run/mosquitto/mosquitto.sock` (через wb-common), не TCP:1883

- Облако Waterius в течение суток перезаписывает показание (последнее выигрывает), любое чтение (имя/значения/доставка) — только за токеном аккаунта, send-ключ пишет вслепую

- Абсолютные импорты полным путём (`from wb.mqtt_waterius.<mod> import …`)

- Полная типизация модулей и тестов

Однострочную форму `"""Текст."""` не используем. Докстринг пишем там, где он говорит то, чего нет в имени и подписи
- Простые чистые функции проверяются доктестами в блоке `Examples`, отдельных юнит-тестов на них нет

## 4. Стратегия решения

### 4.1. Один демон, а не cron

Сервис — постоянный демон (systemd), а не задача cron. Демон нужен, чтобы держать живую
подписку на топики-источники (зеркалить значения в UI в реальном времени), переживать
реконнект брокера и обрабатывать переключатель автоотправки. Расписание проверяется в
цикле опроса (`POLL_INTERVAL` 60 c), сон прерывается событием `_wake_event` при реконнекте
или остановке.

Минута — это точность настройки, которую видит пользователь (время задаётся как `HH:MM`), поэтому
тик не может быть грубее. Ту же гранулярность держат и платформа, и парк: `system_time.js` из
`wb-rules-system` тикает `setInterval(..., 60000)`, таймеры `wb-scenarios` живут на
`cron('0 * * * * *')`. Сна до конкретного дедлайна вместо тика мы не делаем сознательно —
`Event.wait()` отсчитывает таймаут по монотонным часам, поэтому долгий сон после шага системных
часов (контроллер стартует на RTC, NTP переставляет время через минуты) сработал бы со сдвигом, а
минутный тик шаг проглатывает и закрывает пропущенную минуту следующим проходом (4.4). Цена тика
замерена на стенде — 0.05 c CPU за 3 минуты, это 0.03% ядра и ~24 c в сутки.

Сам тик — это две публикации, и остаётся из них одна: `current_time` пишется каждую минуту, он и
меняется каждую минуту, а **`next_execution` — только при изменении**, то есть раз в сутки (так же
устроены `system_time.js` и астрономический таймер сценариев). Памятку последнего опубликованного
значения сбрасывает `_setup_mqtt` — clean-slate вытирает контрол и засеивает его `NO_TIME`, поэтому
уцелевшая памятка оставила бы на карточке `--:--` до завтра.

### 4.2. Раскладка топологии: устройство интеграции + устройство на ключ

- **Устройство интеграции** `/devices/wb_mqtt_waterius` — только статус и управление
  (переключатель, состояние, версия, текущее время, следующая отправка). Без каналов.
- **Устройство-ключ** `/devices/wb_mqtt_waterius_N` (N — 1-based индекс из конфига) —
  на каждый ключ: типизированные каналы-зеркала `ch0..ch3`, время последней отправки,
  последняя ошибка.

Разделение убирает мешанину «статус + данные» в одной карточке и даёт по устройству на
каждый ключ Waterius, как это выглядит и в кабинете.

### 4.3. Clean-slate инициализация

На старте и на каждом реконнекте `clear_all()` затирает все свои retained-устройства в два
скана, затем `create()` создаёт их заново из текущего конфига — так не остаются призрачные
контролы и устройства от прежних конфигов. Первый скан ищет только
наши id (`/devices/+/meta/#` + `/devices/+/controls/+/meta/#`, фильтр по id устройства
интеграции и regex `^wb_mqtt_waterius_\d+$`) — маска `#` ловит и мету одним JSON, и
подтопики полей из старых конвенций. Второй подписывается на `/devices/<id>/#` уже только по
найденным id и гасит всё непустое, что там лежит, — мету, значения, флаги ошибок, залипший
retained в командном топике. Перед гашением фасад снимает подписку на `enabled/on`: скан наших
устройств накрывает и командный топик, а paho отдаёт сообщение ВСЕМ совпавшим фильтрам, поэтому
живой колбэк переключателя получил бы залипшую команду и выключил автоотправку. Порядок
«гасим до подписки» этого не спасал — колбэк переживает сетап, и на втором реконнекте команда
доезжала (воспроизводилось на стенде).

Конец выдачи скан определяет не паузой, а маркером. Брокер набирает retained-набор, пока
обрабатывает подписку, а нашу следующую публикацию обрабатывает уже после него, поэтому
сообщение в свой топик `/wb_mqtt_waterius/marker` (без `retain`, в теле одноразовый токен
скана) приходит последним. Токен нужен, чтобы маркер скана, упёршегося в страховочный
таймаут, не закрыл следующий скан, и чтобы маркер другого нашего процесса, подписанного на
тот же топик, не закрыл наш. Таймаут `DEFAULT_SCAN_TIMEOUT` остаётся только страховкой от молчащего
брокера и ограничивает всю выдачу целиком. На стенде (1129 retained-топиков) выдача 1005
мета-сообщений укладывается в 180-350 мс, после маркера не приходит ничего, а на масках без
совпадений скан заканчивается за 3 мс. Список удаляемых топиков нигде не зашит, удаляется то,
что реально есть в брокере. Своя `/meta` устройства гасится последней, чтобы прерванный прогон
оставил устройство обнаружимым для следующего.

Тот же токен подтверждает и запись — это `wait_for_broker`. На пути демона подтверждения не
ждём: пока процесс жив, `qos1` ничего не теряет, а потерянное гашение самолечится на следующем
реконнекте, где `clear_all` найдёт топик снова. А в `main_cleanup` барьер стоит, потому что за
удалением пакета никто не придёт и недотёртый ретейн повис бы навсегда. Подход взят из
инициализации сценариев (снести всё → создать заново), мерцание UI при рестарте — норма.

### 4.4. Планировщик: плановый фаер + очередь ретрая

`_send_scheduled()` (только автоотправка включена и сегодня разрешённый день):

- **до времени** (`now < HH:MM`) → ждём, не шлём;
- **ровно в назначенную минуту** (`now == HH:MM`) → фаер **всегда**, всем устройствам и
  независимо от отметок: плановое время авторитетно, а смена времени в конфигураторе — это
  новый слот, который в тот же день отработает ещё раз;
- **после минуты** (`now > HH:MM`) → шлём **неотправленных**, то есть устройства без отметки за
  сегодня (`_get_unsent_devices`). Сюда одинаково попадают упавшее устройство, проспанная при
  рестарте минута и сам рестарт; удержанные по 404 ждут следующего слота.

Защита от двойного прохода в одну минуту — `_last_schedule_run`: реконнект будит опрос досрочно,
и без неё слот сработал бы дважды, а упавшее устройство переотправилось бы через секунды. Смена **времени**
отправки сбрасывает даты у всех устройств (новый слот), штампы для карточек при этом остаются.
Ручной `wb-mqtt-waterius send` (`send_now`) правил не соблюдает: шлёт всех независимо от времени
и отметок и переписывает отметки заново.

**Ретрай (case 4).** По итогам пачки устройства раскладываются: OK — дата сегодняшнего дня легла
в `state.json`; транзиентная ошибка (сеть, 503, нет данных канала) — даты нет, устройство осталось
неотправленным; 404 → `_failed_hold` (показываем красным, из дожима исключаем). Отдельной очереди
ретрая нет: каждый цикл опроса (60 c) после назначенной минуты пересчитывается `_get_unsent_devices`
и уходит только он. Поэтому рестарт сервиса ничего не теряет — список вычисляется из состояния, а
не из памяти. Пульт «Есть ошибки» пока `_failed_transient` или `_failed_hold` непусты; обе in-memory,
после рестарта карточка чистая, а первая же попытка вернёт ошибку, если она не ушла. Догон ограничен
календарным днём: после полуночи `now < HH:MM`, и до следующего планового фаера не шлётся ничего.

### 4.5. Персистентное состояние (state.json)

Единый файл `/var/lib/wb-mqtt-waterius/state.json`:
`{enabled, schedule_time, last_sent: {keyhash: {date, stamp}}}`. `date` — день последней удачной
отправки этого устройства, по нему считаются неотправленные; `stamp` — то, что показывает карточка.
Ключи, убранные из конфигуратора, вычищаются из файла на старте сервиса. Переживает рестарт
сервиса И рестарт брокера (persistence у mosquitto выключена — retained-мета не переживает
рестарт брокера, поэтому опираться на неё нельзя). Запись **атомарная**: temp-файл +
`fsync` + `os.replace` — крах во время записи не рвёт боевой файл. Файл пишет ровно один метод
`Service._save_state_values(**values)`: он обновляет переданные ключи и сохраняет состояние под
`threading.Lock` (paho-поток `_on_toggle` против main-потока `send_now`). Штамп устройства
пишется сразу после его ответа, а не одной записью на всю пачку, поэтому падение посреди пачки
сохраняет штампы уже отправленных.
Ключи в `last_sent` — это `state.key_hash` (sha1[:12], живёт рядом со своим единственным
потребителем), сырой ключ в файл состояния не попадает. Сам ключ и так лежит открытым в конфиге,
поэтому смысл не «секрета нет на диске», а «секрет в одном файле, а не в двух» — второй файл
забирают бэкап контроллера и диаг-архив.

### 4.6. Защита от частичного/сдвинутого payload

Waterius мапит показания по номеру канала (`ch0..ch3`). Если у устройства не пришло значение
топика, нельзя просто выкинуть канал — уплотнение индексов сдвинуло бы остальные и записало
показания не в те слоты кабинета. Поэтому снимок каналов делает `_get_snapshot()`, и если хоть
одного значения нет — **это устройство не шлём** целиком и ставим ему ошибку.

Перед отправкой, и плановой и dry-run, `_await_readings()` ждёт появления значений — но не
глухой паузой, а проверкой каждые `READINGS_POLL` (0.2 c) в пределах `READINGS_TIMEOUT` (5 c).
В норме значения retained и приходят сразу после SUBSCRIBE, поэтому первая же проверка
проходит и ожидания нет вовсе; пауза нужна только на гонку «отправка через секунды после
старта сервиса». Дожим ждёт так же: таймаут ограничен пятью секундами и тратится только когда
за сегодня кто-то ещё не отправлен. Не пришло значение — устройство остаётся неотправленным и
повторяется раз в минуту, подтянувшееся позже значение подхватится там.

Показание передаётся в `build_payload` не словарём, а фрозен-датаклассом `ChannelReading`
(`topic`, `type`, `value`, `serial`) — форма входа объявлена типами, а не угадывается по
`.get()`, и совпадает по стилю с `SendResult` на выходе.

В `build_payload` ветки «пропустить пустой канал» нет по той же причине. Функция требует значение
у каждого канала и на пустом поднимает `ValueError` с маскированным ключом устройства и топиком
канала, а инвариант держит вызывающий — `_send_device` снимает снапшот, проверяет пропуски и до
сборки тела не доходит.

Обрезки списка каналов в `build_payload` тоже нет: число каналов проверяется при загрузке
конфига (`_parse_device` роняет ConfigError на >`MAX_CHANNELS`, константа живёт там же, рядом
со своей единственной проверкой), а схема конфигуратора даёт
`maxItems: 4`. Дублировать проверку в сборщике тела не за чем.

### 4.7. Реконнект брокера

`on_connect` постоянный, а не одноразовый — на каждом (ре)коннекте ставит `_resetup_event`,
цикл `run()` реагирует и вызывает `_setup_mqtt()` из главного потока (clean-slate → publish
→ subscribe → restore enabled → refresh). Так рестарт mosquitto (например при обновлении
homeui) не оставляет сервис без переопубликованных устройств.

### 4.8. Отправка: пауза и ретраи

Клиент API — объект `WateriusClient` (эндпоинт, таймаут, число попыток, backoff и одна
`requests.Session`), а не функция с семью аргументами. Сессия переиспользуется, поэтому три ключа подряд идут по одному
TLS-соединению, а не открывают его заново на каждый POST.

**Время жизни клиента — одна пачка отправки.** Он создаётся в `_send_devices_data` как контекстный
менеджер и закрывается на выходе из пачки, поэтому сессия живёт ровно столько, сколько от неё
есть польза. Держать её всё время работы демона незачем: между суточными отправками
переиспользовать нечего, к следующему разу сервер соединение уже закрыл, а закрытый им сокет до
первого обращения висит в `CLOSE_WAIT`. Клиент владеет своей сессией единолично, снаружи её
передать нельзя — поэтому `close()` безусловный, а `__exit__` гарантирует его вызов даже когда
отправка падает с исключением. Дожим неотправленных — отдельная пачка со своей
сессией, то есть свой TLS-хендшейк раз в минуту — при аварии это незаметная нагрузка.
`--dry-run` идёт отдельным методом
`dry_run_payloads()`, который только собирает и печатает payload'ы, поэтому клиента там нет
вовсе и признак `dry_run` больше не протаскивается через пачку отправки.

Несколько ключей шлются с паузой `SEND_GAP` (1.5 c) между POST — nginx у Waterius 503-ит
пачку подряд. `WateriusClient.send` ретраит транзиентные статусы `{429, 502, 503, 504}` и
сетевые ошибки (линейный backoff). И пауза `SEND_GAP`, и backoff ретраев прерываются
`self._stop.wait()` — shutdown отзывчив, обрыв в паузе оставляет недосланные устройства без
отметки за сегодня.
Событие остановки передаётся в `WateriusClient.send` параметром `stop: Optional[threading.Event]`, и backoff
ждёт на нём вместо `time.sleep`. Без события создаётся никогда не поднятое — тогда ожидание
ведёт себя как обычный сон, и отдельной ветки в коде не нужно. Просто `time.sleep` тут не годится:
по PEP 475 с Python 3.5 он после сигнала досыпает остаток, то есть SIGTERM не сократил бы ни
backoff, ни `SEND_GAP`.

HTTP 404 — жёсткая ошибка «ключ не разрешён в устройство» (неверный или отозванный ключ). Внутри
`send` она не ретраится и отдаётся с внятным текстом `KEY_NOT_FOUND_ERROR` в `last_error`, а
раскладку исхода по `_failed_hold` и `_failed_transient` делает планировщик (4.4).

### 4.9. Ключ как write-only credential

Валидный ключ → HTTP 200 с пустым телом. Неразрешимый в устройство ключ (неверный,
отозванный, несуществующий) → HTTP 404, битый JSON → 400. То есть с 2026-07 неверный ключ
драйвер ловит как ошибку (404 → красный `last_error`). Но тело успешного ответа пустое —
имени устройства и подтверждения записи там нет, поэтому **HTTP 200 = принято сервером, а
не гарантия, что значение верно легло в кабинет** (единицы/каналы проверяются в кабинете или
обратным API под токеном аккаунта). «Активен» означает «принято сервером». Ключ маскируется (не более первых 5
символов, короткий ключ целиком не раскрывается) в заголовках безымянных устройств
(LAN-читаемый MQTT) и в логах. В самом конфиге `/etc/wb-mqtt-waterius.conf` ключ лежит
открытым текстом (0644 conffile, норма confed-конфигов WB) — чтение требует локального
доступа к контроллеру, не LAN. Единственное место, где credential не маскируется, осознанно.

### 4.10. Название устройства

Поле `name` элемента `devices` кладётся в тело POST **всегда**, и Ватериус переименовывает
устройство на площадке при каждой отправке. Проверено живьём 2026-07-27 (тест 7 в
`empirical-tests.md`): непустое имя меняет название сразу, пустая строка сервером
**игнорируется** (текущее название не затирается), кириллица проходит. Отдельного вызова
переименования в API нет, имя в ответе не возвращается — подтверждение только в кабинете.

Раз пустая строка сервером игнорируется, отдельной ветки «не кладём пустое имя» в
`build_payload` нет — она бы усложняла код ради поведения, которое и так совпадает.

В схеме поле идёт вторым, после ключа (`propertyOrder` 1 у `key`, 2 у `name`, 3 у `channels`),
обязательное, но с пустым значением и проверкой только на длину (30 символов). Пустое имя — это
осознанный режим «название веду в кабинете Ватериус руками». Тем же полем подписывается
WB-устройство ключа — `Ватериус - <имя>`, а без имени `Ватериус - <5 символов ключа>`.

В логах и сообщениях об ошибках устройство обозначается **маскированным ключом**, не именем:
ключ — стабильный идентификатор, а имя пользователь меняет в конфигураторе и может задать
одинаковое сразу нескольким устройствам.

### 5.4. Командная строка (main.py)

Полный набор команд и флагов. В README вынесены только те, что нужны пользователю, —
`daemon`, `send`, `send --dry-run` и `--version`.

| Команда / флаг    | Что делает                                                              |
| ----------------- | ----------------------------------------------------------------------- |
| `daemon`          | Запуск демона, этим занимается systemd-юнит                             |
| `send`            | Разовая отправка сейчас, игнорирует отметки за сегодня и переключатель  |
| `send --dry-run`  | Собирает и печатает payload, в облако не ходит                          |
| `cleanup`         | Снимает все устройства сервиса из MQTT, зовётся из `prerm` при удалении |
| `-c` / `--config` | Другой файл конфигурации вместо `/etc/wb-mqtt-waterius.conf`            |
| `--version`       | Версия установленного пакета из метаданных, ленивое чтение              |
| без команды       | Печатает help и выходит с `EXIT_FAILURE`                                |

`cleanup` и `-c/--config` в README намеренно не описаны. Первый снимает устройства из MQTT
и нужен только процедуре удаления пакета, второй уводит сервис с конфига, который правит
конфигуратор, и в обоих случаях ручной запуск пользователем чинит не проблему, а создаёт её.

Без команды демон не стартует намеренно. Он бы занял MQTT-идентификатор работающего
сервиса и выбил бы его с брокера.

## 6. Схема JSON (UI)

`_format: grid-strict` в корне; поля:

- `send_time` — время (`_format: time`), grid 6, своя строка
- `days` — дни недели (`_format: checkbox`, minItems 1, required), grid 12
- `devices` — массив устройств (`array_controls_top`, `disable_array_delete_last_row`)
  - `name` — название устройства (required, но пустая строка допустима, `maxLength` 30,
    headerTemplate `{{self.name}}`)
  - `key` — ключ Waterius
  - `channels` — массив каналов (до 4)
    - `topic` — контрол-источник (`_format: wb-autocomplete`, паттерн `device/control`)
    - `data_type` — тип счётчика (enum 0..9, названия по кабинету Waterius)
    - `serial` — опциональный серийный номер

Переводы — синтетические camelCase-ключи (`waterius*`), полный паритет en/ru.

## 7. MQTT-топология и статусы

### 7.1. Устройство интеграции `/devices/wb_mqtt_waterius`

| Контрол          | Тип            | Описание                           |
| ---------------- | -------------- | ---------------------------------- |
| `enabled`        | switch         | Интеграция включена (автоотправка) |
| `state`          | value + enum   | Состояние (см. ниже)               |
| `version`        | text, readonly | Версия пакета                      |
| `current_time`   | text, readonly | Текущее время                      |
| `next_execution` | text, readonly | Следующая отправка (или `--:--`)   |

Числовой enum `state`: `0` Инициализация запущена, `1` Настройки не корректны, `2` Отключен,
`3` Активен, `4` Есть ошибки. Код `0` первым — при clean-slate `state` кратко уходит в
пустое, homeui рисует пустой enum как код 0, поэтому 0 = «Инициализация», а не «ошибка».

`create()` сразу даёт значение всем пяти контролам (время — плейсхолдером `--:--`), потому что на
битом конфиге дальше не публикуется ничего: иначе карточка показывала бы «Настройки не корректны»
рядом с переключателем без положения.

### 7.2. Устройство-ключ `/devices/wb_mqtt_waterius_N`

| Контрол      | Тип             | Описание                                       |
| ------------ | --------------- | ---------------------------------------------- |
| `last_sent`  | text, readonly  | Время ответа Ватериуса на отправку этого ключа |
| `ch0..ch3`   | value (+ units) | Зеркала показаний, единицы по типу             |
| `last_error` | text, readonly  | Ошибки — последняя ошибка (краснеет при сбое)  |

Заголовок канала — по типу счётчика (`DATA_TYPE_CONTROLS`). Если в одном ключе тип повторяется, к
заголовку дописывается короткое имя контрола-источника (`Электричество (День) (electricity_day)`),
а не полный топик — иначе homeui обрезал бы различающий хвост многоточием.

### 7.3. Модель ошибок

По одному контролу, не «всё устройство»:

- Настройки не корректны (нет устройств) → красный `state` на устройстве интеграции + `state=1`
- Сбой отправки устройства (API-ошибка или нет данных каналов) → красный `last_error` этого
  устройства-ключа; агрегат на устройстве интеграции `state=4` «Есть ошибки»
- Успех → `last_sent` проставлен, `last_error` очищен, краснота снята

Флаг в `meta/error` ставится значением `w`: по конвенции это ошибка записи, а у нас отказывает
именно выгрузка показаний наружу. Значение `r` обещало бы последнее хорошее показание в самом
контроле, чего у `last_error` нет. Тот же контрол может покраснеть и без нас: если демон умер
без штатной остановки, флаг ставит сам брокер, но значением `rw` — см. 9.9.

Штамп `last_sent` берётся в момент ответа по этому устройству, а не один на всю пачку.
Устройства шлются по одному с паузой `SEND_GAP`, а ошибочное дожимается раз в минуту, поэтому
общий штамп показывал бы медленное устройство отправленным тогда, когда ответило быстрое.

## 8. Параметры конфигурации

| Параметр    | Тип    | Обязательный           | Описание                                      |
| ----------- | ------ | ---------------------- | --------------------------------------------- |
| `send_time` | string | да (дефолт `03:00`)    | Время отправки `ЧЧ:ММ`                        |
| `days`      | array  | да                     | Дни недели (`monday`..`sunday`), минимум один |

Пустой список устройств валиден — состояние свежей установки, сервис не падает, показывает
«Настройки не корректны».

## 9. Граничные случаи

### 9.1. Битый/отсутствующий конфиг

`main_daemon`/`main_send_once` ловят `ConfigError` от `load_config()` → `_report_config_error()`
красит устройство интеграции в «Настройки не корректны» (чтобы UI не показывал старое
«Активен» при мёртвом сервисе) → `return EXIT_CONFIG_ERROR (6)`. Юнит имеет
`RestartPreventExitStatus=6` — сервис не крутится в краш-лупе, поднимается когда конфиг
сохранят в UI (confed перезапустит сервис).

### 9.2. Битый state.json

`load_state` при непарсящемся JSON или JSON-не-объекте (`[]`) возвращает дефолты, не падает.

### 9.3. Рестарт брокера mosquitto

Retained-мета устройств пропадает, но сервис по `_on_connect` переопубликует всё (см. 4.7).
Проверено вживую — устройства сами возвращаются за ~8 c без перезапуска сервиса.

### 9.4. Значение канала не пришло

Устройство не шлётся целиком, ему ставится ошибка, и отметки за сегодня оно не получает, то есть
остаётся в дожиме как транзиент — значение может подтянуться позже (4.6, 4.4). Частичный или
сдвинутый payload в кабинет не уходит никогда.

### 9.5. Повторная отправка в тот же день

Слот срабатывает за минуту ровно один раз (`_last_schedule_run`), а после него автоотправка берёт
только устройства без отметки за сегодня, поэтому успешно отправленное до конца дня не повторяется
(правила и раскладка ошибок в 4.4). Смена времени в конфигураторе сбрасывает отметки и даёт ещё один
слот в тот же день. Ручной `wb-mqtt-waterius send` отметки не проверяет и работает всегда.

### 9.6. Обрыв (SIGTERM) в паузе между устройствами

Флаг `aborted` → `send_now` возвращает `False`, а недосланные устройства остаются без отметки за
сегодня, поэтому после запуска сервиса их забирает первый же проход расписания и до завтра они не
«теряются».

### 9.7. Мёртвый/отозванный/несуществующий ключ

HTTP 404 → устройство краснеет `last_error` с текстом «ключ не принят» и уходит в hold без
ретрая (4.8, 4.9).

### 9.8. Смена набора устройств

`key_hash`-карта `last_sent` прунится до текущих устройств при старте; clean-slate убирает
устройства-ключи, которых больше нет в конфиге.

### 9.9. Внезапная смерть демона (SIGKILL, OOM)

Перед подключением демон регистрирует у брокера Last Will на
`/devices/wb_mqtt_waterius/controls/state/meta/error` — значение `rw`, `retain`. Умерли без
штатной остановки → брокер сам красит «Состояние», и карточка не показывает «Активен» от
мёртвого сервиса. Значение `rw`, а не `w` как у живой ошибки: мёртвый демон не может ни читать,
ни писать, так же помечает свой bridge и `wb-mqtt-zigbee`. Штатный `stop()` Last Will снимает
(брокер отбрасывает его при нормальном DISCONNECT), а следующий здоровый старт снимает флаг
вместе с остальным ретейном в clean-slate. Одно соединение несёт один Last Will, поэтому цель —
устройство интеграции, у ключевых устройств своё состояние остаётся прежним до перезапуска.

### 9.10. Ручной `send` при живом демоне

У ручной отправки свой client id (`wb-mqtt-waterius-send`), поэтому демона с брокера она не
выбивает (одинаковый id выбил бы). А вот `state.json` у процессов общий, межпроцессного лока нет.
Запись атомарная, полуфайла не будет, но выигрывает последний писатель: демон держит свою копию
состояния в памяти и на следующем сохранении затрёт отметку, поставленную ручной отправкой.
Последствия косметические — демон может отправить ещё раз (в плановую минуту он это делает и так,
см. 9.5), либо штамп «Отправлено» на карточке окажется от другого процесса. Файловый лок не заводим сознательно: он защищал бы поле, которое влияет только на
отображение и на повтор, а повтор у нас безопасен — сервер Waterius хранит одно показание в
сутки. Отдельная гоча проб: ручной прогон с урезанным конфигом через `-c` прунит штампы
устройств, которых в этом конфиге нет, потому что путь состояния фиксированный и флагом не
подменяется.

Топик взят контрольный, а не device-level `/devices/<id>/meta/error`, который конвенции и наша
дока для интеграций называют штатным местом LWT: homeui разбирает ошибку только на уровне
контрола, а device-level читает лишь страница Device Manager, поэтому на карточке интеграции
такой флаг никто не увидел бы. Отступление осознанное, к нему стоит вернуться, если homeui
начнёт показывать device-level ошибку.
